# Task 56 — recovery fix review (design only)

**Scope:** one locally deployed machine. This document proposes changes for Tech Lead review; it does not implement them. No service, serial port, payment, inventory record, firmware, or physical actuator was touched during this review. Branch reviewed: `feat/task56-power-reboot-acceptance`.

## Evidence and decision boundary

The project owner reports **PASS** for 56-A, 56-B.1, 56-B.3 (manual recovery), 56-C, 56-D, 56-E, 56-F.1, and 56-F.2; **FAIL** for 56-B.2 (automatic USB Serial recovery); and **NOT TESTED** for 56-F.3 (interrupted unlock across restart) and 56-G (controlled power loss). These are owner-provided physical results, not observations made in this review. They do not prove restart-safe deduplication. The prior [Task 56 preparation](task56-power-reboot-acceptance.md) and [Task 55 hardware review](task55-firmware-hardware-source-of-truth.md) remain the source-reviewed baseline.

The owner observed `/dev/ttyUSB0` before USB disconnect and `/dev/ttyUSB1` afterward. The installed Pi environment was manually changed to `ESP32_SERIAL_PORT=/dev/serial/by-id/usb-1a86_USB_Serial-if00-port0`; a manual Pi service restart then restored sensor readings. This demonstrates that the stable path worked in that acceptance session. It does not establish automatic reconnect or prove that every future replacement board will have the same by-id path.

## Source-based root causes

### 1. USB Serial reconnect

[`Esp32SerialClient.connect()`](../edge/serial_client.py) opens one configured path and stores one `serial.Serial` handle. `is_connected` checks only `is_open`, so an unplugged but stale handle can appear connected until I/O fails. [`main()`](../edge/pi_unlock_service.py) calls `connect()` only at service startup. Neither `/health` nor `/hardware/status` reconnects, and `/health` does not exchange a `PING`/`PONG` with the ESP32. The status route holds `serial_operation_lock`, clears the input buffer, sends `GET_STATUS`, and returns 503 on incomplete/error status; it does not repair the connection. Systemd retries a process that exits on startup failure, but it cannot repair a live process holding a stale handle. A fixed `/dev/ttyUSB0` setting also fails after Linux renumbers the device.

### 2. Restart-safe unlock deduplication and payment authority

[`/unlock`](../edge/pi_unlock_service.py) checks only that `slotNumber` is 1–3 and `transactionId` is a positive integer. It never asks the backend whether that transaction is paid, uncancelled, and bound to the requested slot. The `unlock_transaction_outcomes` dictionary suppresses duplicates only for the life of one Flask process; it is empty after restart. Its `UNLOCKED` value currently means that `open_slot()` returned after a Serial write, not that the firmware accepted the command or a lid opened.

The kiosk calls `/unlock` only after observing backend `SUCCESS`, and persists `ATTEMPTING` before that call. A browser reload with `ATTEMPTING` shows assistance rather than replaying; `NOT_STARTED` may attempt an unlock, while `UNLOCKED` restores the success screen. These are useful browser guards, but they cannot authorize arbitrary HTTP callers or protect against a Pi service restart and a repeated request. See [HomePage](../frontend/src/pages/HomePage.tsx), [payment recovery](../frontend/src/active-payment-recovery.mjs), [payment flow](../frontend/src/payment-flow.mjs), and [unlock API](../frontend/src/api/unlock.ts).

The [backend transaction service](../backend/src/services/transaction.service.ts) verifies/reconciles Opn payment and atomically stores `SUCCESS` plus `SOLD_OUT`; cancellation is separately guarded. The [schema](../backend/prisma/schema.prisma) has no fulfillment attempt record, and the [routes](../backend/src/routes/transaction.routes.ts) expose no atomic unlock claim. `SUCCESS` proves a sale in the backend model, not physical dispensing. The existing payment status response is a read/reconciliation API, not an idempotent authorization to actuate.

### 3. ESP32 ACK and mixed Serial responses

[`open_slot()`](../edge/serial_client.py) writes `OPEN:n\n`, flushes, and returns without reading. The [firmware](../firmware/vending_esp32.ino) can emit `ACK:OPEN:n`, `ERROR:BUSY`, `ERROR:INVALID_SLOT`, `LOCK:n:OPENED`, and later `LOCK:n:CLOSED`; unsolicited `DOOR` and `IR` lines share the stream. The Pi status collector's buffer clear can discard a late unlock response once the current write-only unlock has released the Serial lock. A written command could be rejected, accepted with a lost ACK, or never reach the device. The current protocol has no request ID; `ERROR:BUSY` has no slot, and a delayed `ACK:OPEN:n` can be mistaken for a later same-slot command. Therefore the v1 protocol permits **best-effort response observation**, not guaranteed correlation or exactly-once physical actuation. `ACK` means firmware accepted a command; `LOCK` describes relay control; only the reed sensor speaks to door position, and it does not prove a product was dispensed.

## Options and recommendation

| Finding | Option | Trade-off / decision |
| --- | --- | --- |
| Reconnect | Stable `/dev/serial/by-id/...` setting plus manual service restart | Already demonstrated by owner; simple operational fallback, but 56-B.2 remains failed. |
| Reconnect | Stable path plus one bounded background reconnect/liveness worker | **Recommend.** Recovers without restarting Chromium or the Pi. Requires strict ownership of the Serial handle and fail-closed readiness. No command queue. |
| Deduplication | Pi-local SQLite or fsynced journal keyed by transaction | Can survive a Pi process restart, but still needs backend payment validation, careful disk durability, and coordination with backend sale state. Local disk loss or backup restore can erase history. Not the primary authority for this prototype. |
| Deduplication | Backend PostgreSQL unlock claim, unique by transaction, committed before Serial send | **Recommend.** One durable authority can atomically check paid/uncancelled/slot binding and consume the sole attempt. A crash after the claim may strand an unattempted sale; staff reconciliation is the deliberate safe outcome. |
| ACK | Keep write-only response | Minimal code change, but cannot distinguish firmware rejection from accepted write. Not sufficient for a truthful accepted-command result. |
| ACK | Serialize v1 command and bounded ACK/error read | **Recommend as an interim improvement** with ambiguous outcomes treated as uncertain. No automatic resend. Stale/missing replies still prevent a hard correlation guarantee. |
| ACK | Protocol v2 with echoed request ID on command, ACK/error, and relay-cycle messages | Needed for reliable request/reply correlation. Requires firmware and Pi compatibility work, version negotiation, and a separately approved flash. It still cannot prove physical dispensing or exactly-once actuation after a crash. |

### Recommended minimum viable design

1. **Reconnect manager:** Configure the installed Pi service with the validated by-id path. One Serial owner controls `DISCONNECTED → CONNECTING → READY` and a `FAULT`/backoff state. Detect read/write exceptions, missing `PONG`, or incomplete status; close the stale handle under the Serial lock. Reopen only the configured stable path with finite open/read timeouts and capped exponential backoff (for example 0.5, 1, 2, 5 seconds, then 5-second attempts). Each attempt is bounded; retry may continue while the process runs. A successful open alone is not ready: observe a fresh `PONG` and complete `GET_STATUS` before setting `READY`. `/health` returns 503 for stale/unverified readiness and 200 only for a recently verified ESP32 response, with a timestamp/age and `mockHardware` distinction. `/hardware/status` returns 503 promptly while disconnected and resumes normal fresh reads after recovery. Reconnect never stores or replays `OPEN`.
2. **Backend-authorized durable claim:** Add a one-machine `UnlockAttempt` record with a unique `transactionId`, bound `slotNumber` and machine identity, creation time, and states such as `RESERVED`, `ACK_ACCEPTED`, `REJECTED`, and `UNCERTAIN`. Add a Pi-only internal claim interface authenticated with a machine credential kept out of the browser and repository. In one serializable DB transaction, check the transaction exists, is `SUCCESS`, is not customer-cancelled, has the requested slot, and belongs to this pilot machine; then insert the unique claim. A duplicate or mismatched request returns the existing state without authorizing another send. If a pending record needs provider reconciliation, perform that before the claim; provider/backend unavailability fails closed. Do not change payment status, slot status, cancellation, or sale notification behavior. Set a finite network timeout on the Pi claim request; if its response is lost, query the claim for reconciliation **without** sending `OPEN`.
3. **At-most-one dispatch:** The Pi checks `READY`, obtains a nonblocking machine actuation mutex, obtains the backend claim, rechecks the Serial generation/readiness, then sends at most one `OPEN` while holding the Serial operation lock through its bounded reply window. A durable claim is committed **before** any bytes are sent. On restart, unresolved claims stay consumed and inhibit replay. An unresolved in-flight claim also keeps the machine actuation gate closed until staff reviews it; this gate must be durable in the backend, not just a Python mutex. Explicit `ERROR:BUSY`, timeout, disconnect, malformed/conflicting replies, and lost outcome updates go to a non-retryable staff-reconciliation state. `ACK:OPEN:n` can mark command acceptance, never physical success. Release the actuation gate for the next sale only after a reviewed completion condition (at minimum the observed relay-cycle end and a conservative timeout); loss of that evidence keeps the gate closed. No HTTP request waits in a queue for an eventual reconnect.
4. **Truthful kiosk contract:** Keep `SUCCESS`/`SOLD_OUT` as sale authority. Update the Pi response and kiosk labels so `COMMAND_ACCEPTED` means observed firmware acceptance, not an opened lid. Duplicate `RESERVED`/`UNCERTAIN` responses show assistance and never call `/unlock` again. A persisted browser `ATTEMPTING` remains assistance. Migrate the current local-storage `UNLOCKED` state conservatively: old data must never trigger a new unlock and must not be treated as physical proof. Browser persistence is a usability guard; the backend claim is the restart-safe guard.

The machine credential limits the internal claim endpoint to the Pi service; binding it to the one machine and matching the DB slot prevents an unpaid, cancelled, or unrelated transaction from authorizing `OPEN`. Keep the Pi HTTP service loopback-only in production. The current customer flow has no customer identity or secret in the browser, so a local caller who learns an eligible paid transaction ID could still race the kiosk for its **single** claim. That is a remaining authorization limitation requiring host access controls or a separate end-to-end customer capability design. CORS alone is not authentication. Do not enable `MOCK_HARDWARE` in physical deployment or let mock calls consume live claims.

### Failure and crash windows

| Failure point | Durable state and required behavior |
| --- | --- |
| Before claim commits | No Serial write is allowed. The caller may retry the authorization request after backend recovery. |
| Claim commits; response lost or Pi crashes before write | `RESERVED` remains and blocks another physical send. Staff determines that no actuation occurred before any separately authorized fulfillment. This sacrifices automatic liveness to preserve at-most-one dispatch. |
| Serial write begins, then times out/disconnects/crashes | Whether ESP32 acted is unknowable from the Pi. Keep claim `UNCERTAIN` or unresolved, inhibit repeat, inspect logs and physical state, then reconcile manually. A write exception is not proof of no actuation. |
| ACK arrives but DB outcome update or Pi HTTP response is lost | Claim still blocks resend. Read-only claim lookup can restore an accepted/uncertain UI state; no recovery path may issue a second `OPEN`. |
| `ERROR:BUSY` or `ERROR:INVALID_SLOT` is read | Record a rejection/uncertainty and request staff review. With v1's uncorrelated error line, do not assume it belongs definitively to this attempt or automatically retry. |
| Backend database restored from an old backup, Pi storage lost, or firmware resets mid-pulse | The claim history or physical outcome can diverge. Stop unattended vending and reconcile against provider, DB, Pi logs, and physical cabinet before reopening. Neither ACK nor a DB row guarantees physical dispensing. |

The durable-claim-before-send order yields **at-most-one application dispatch while the claim record remains intact**, not exactly-once actuation or dispensing. The lost-claim/backup-restore and manual intervention cases remain explicit limits. A staff-assisted separate fulfillment must be an audited workflow, never a replay of the same `/unlock` request.

## Serial ownership and response design

- Use one read path for the Serial stream. `PING`, `GET_STATUS`, and `OPEN` each acquire the same operation lock for their complete request/response window. Reconnect/close/swap of the handle uses that lock too, with a generation number so a response from an old handle cannot complete a new command. A second status request should receive a bounded busy response rather than wait indefinitely behind an unlock. A second unlock should receive busy/uncertain feedback immediately; it must never be queued.
- Do not clear the input buffer while an unlock response is outstanding. Change `/hardware/status` to use the shared reader; retain unrelated `DOOR`/`IR` change events as observations without letting them satisfy a stale snapshot. For v1, drain/log stale lines only before a command in a known idle window, then write `OPEN:n` and wait for a matching `ACK:OPEN:n` or an explicit error within a short bounded timeout. An unexpected `READY`, mismatched ACK, disconnect, or timeout makes the result uncertain. Draining cannot eliminate delayed same-slot ACKs, so v1 acceptance remains best effort.
- If Tech Lead requires a **reliably correlated** ACK, add a negotiated v2 command carrying a unique attempt ID and echo it in `ACK`, `ERROR`, and relay-cycle responses. Do not send v2 commands to old firmware. Include a version handshake and fail closed on mismatch; firmware changes and flash are a separate approval. Even v2 only confirms firmware-level events. Reed readings and visual/product observation remain separate evidence of physical state.
- On disconnect while an unlock is in flight, never reconnect and resend that command. Reconnect may restore **read-only** status and readiness; the backend claim remains consumed and the machine remains inhibited pending reconciliation.

Proposed internal API contract (names illustrative): `POST /api/v1/internal/unlock-claims` with `{transactionId, slotNumber, machineId}` from authenticated Pi; `201 {claimId, state:"RESERVED"}` only for a new claim; duplicate returns `200 {state, dispatchAllowed:false}`; mismatched/unpaid/cancelled returns 4xx; backend/provider outage returns 503. `PATCH /api/v1/internal/unlock-claims/:claimId` records observed ACK/error/uncertainty but can **never** set `dispatchAllowed:true` again. `GET` supports read-only reconciliation. All transitions are monotonic, auditable, and constrained to the claimed machine/slot. The credential is configured on Pi and backend, never sent to the kiosk.

## Non-actuating test strategy

1. Serial fakes emulate `/dev/ttyUSB0` disappearing and a stable by-id path resolving to a new port. Simulate stale `is_open`, read/write exceptions, missing `PONG`, incomplete six-line status, repeated disconnects, and successful reconnect. Assert `/health` is 503 until a fresh probe succeeds, `/hardware/status` recovers, backoff is capped, and no `OPEN` is emitted by reconnect/status paths.
2. Use a fake Serial stream with interleaved `DOOR`/`IR`, `READY`, `ACK`, `ERROR:BUSY`, delayed same-slot ACK, and disconnect at every write/read boundary. Assert the status collector never steals an unlock response; ambiguous v1 sequences remain uncertain; concurrent status/unlock requests do not deadlock or overlap; no command is queued or replayed after reconnect.
3. Backend tests use an isolated test DB or transactionally mocked store to race two claims, verify the unique constraint and machine gate, and cover PENDING, FAILED, EXPIRED, cancelled, mismatched slot, missing transaction, already claimed, and verified SUCCESS. Assert neither payment nor inventory semantics change. Auth tests reject absent/invalid machine credentials; timeout/retry tests never create a second dispatch right.
4. Pi tests inject fake backend and Serial clients. Crash/fault injection at pre-claim, post-claim/pre-send, partial write, post-ACK/pre-outcome-update, and response-loss boundaries. Restart the service object/process against the same test claim store and assert **zero or one** `OPEN`, never two. Test `MOCK_HARDWARE` in a separate isolated mode without a live claim.
5. Frontend tests cover old and new storage schema, `NOT_STARTED`, `ATTEMPTING`, accepted and uncertain outcomes, duplicate claim responses, backend outage, and reload. A duplicate/uncertain outcome must show assistance without calling `/unlock` again or claiming physical success.

All test ports, backend calls, and payments must be fakes or isolated test fixtures. No physical Serial port, real unlock, production inventory, live provider charge, service restart, flash, or power action belongs in automated validation. Existing tests already cover process-local Pi duplicate suppression and browser recovery, but they do not exercise the proposed durable claim or live USB renumbering.

## Physical regression plan after approval and implementation

Retain the owner-provided PASS results as baseline; recheck affected behavior rather than treating prior PASS as proof of new code. With an approved cabinet session, safe fixture, test-mode payment, and evidence capture per [Task 56 runbook](task56-power-reboot-acceptance.md):

1. Verify the installed by-id symlink resolves uniquely and the service is `READY`; inspect exact `/health` readiness age, read all three sensors, and confirm relays are off.
2. At idle, disconnect/reconnect USB and observe renumbering. Without restarting Pi service or Chromium, require a 503/not-ready interval followed by fresh `PONG`/status and valid IR/Reed readings for all slots. Require zero `OPEN` commands and zero relay pulses. Repeat with the device absent long enough to exercise capped backoff.
3. In an approved non-actuating test harness, present unpaid, cancelled, wrong-slot, duplicate, and concurrent claims; require no Serial `OPEN`. For a single separately approved Opn Test Mode dispense, require exactly one backend claim and at most one observed `OPEN`. Record ACK/ERROR and independent reed/product observations without equating them.
4. For 56-F.3, inject or stage an interrupted unlock only under an owner-approved physical safety procedure; inspect claim state after Pi service restart. A second same-transaction request must not produce `OPEN`; uncertain state must lead to assistance. If a safe interruption cannot be staged, mark this physical case BLOCKED, not PASS.
5. Recheck 56-A, 56-C, 56-D, 56-E, and payment/session recovery after deployment. 56-G remains a separate owner-approved controlled power-loss test; never cut power during payment, DB write, firmware flash, or pulse.

Capture timestamps, transaction/claim IDs, backend and Pi logs, Serial protocol lines, sensor readings, and physical observations with credentials redacted. Stop on any unexpected relay activation, duplicate command, claim mismatch, or database/inventory drift.

## Reviewable phases, release gate, and rollback

1. **Phase 1 — Serial recovery:** stable path documentation, reconnect manager, accurate health, read-only status recovery, fake-port tests. Review and deploy independently; keep unlock fail-closed during any disconnect. Roll back Pi package/config to the last reviewed version and use the proven manual by-id restart procedure if needed.
2. **Phase 2 — payment-authorized durable dispatch:** backend migration/internal claim plus Pi caller and machine gate, then frontend duplicate/uncertain-state handling. Review backend migration and API first, then Pi/frontend in a coordinated release. Phase 2 must fail closed when the backend claim service is unavailable. Do not enable live payment-driven unlock until the claim path and non-actuating crash tests pass. Preserve claim rows on rollback; do not drop or reset them, or an earlier transaction could unlock again.
3. **Phase 3 — response fidelity:** shared Serial reader, v1 bounded ACK/error observation, status coexistence, truthful response/UI. Review separately but release together with Phase 2 for unattended vending; before Phase 3, any post-write outcome should be treated as unconfirmed and routed to staff. If reliable correlation is an acceptance requirement, plan a later approved v2 firmware/host protocol rollout with version handshake and rollback image. Old firmware must never be silently sent v2 commands.

During any partial deployment or rollback, disable unattended unlock and route paid customers to staff assistance if API/schema versions disagree, claim history is unavailable, or the machine gate is unresolved. Run database migrations with backup and compatibility review; a rollback must keep the durable claim history intact. No automatic physical retry is proposed in any phase.
